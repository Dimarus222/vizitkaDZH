# Сайт-визитка Дмитрия Жданова — инструкция

Кибер/infosec-стилизованный сайт-визитка с каталогом реальных проектов,
формой заявок и полноценной админ-панелью. Backend на чистом Go (без внешних
зависимостей), frontend на HTML/CSS/JS. Готово к деплою на Railway через Docker.

## Про каталог проектов

В комплекте — 6 карточек-заготовок, по одной на каждую ключевую часть
стека: REST API/backend, full-stack веб-приложение, десктоп, DevOps/Docker,
security-аудит и realtime-приложение. Технологии в описаниях соответствуют
реальному стеку (Go, Python, C#, C++, JS) — без придуманных фреймворков.

Каждая карточка — заготовка: описание и список фич уже написаны, но поле
`demo_url` (ссылка на демо/GitHub) изначально пустое. Добавляйте ссылку на
реальный код/демо через админ-панель по мере готовности каждого проекта —
кнопка «Перейти на сайт →» на карточке появится автоматически, как только
поле заполнено. Пустые карточки без ссылки — это нормально, лучше честно
показать 6 работающих демо, чем 6 битых ссылок.

Через админ-панель можно редактировать, удалять и добавлять карточки —
меняйте название, описание, стек и ссылку под свои реальные проекты.

## Список файлов (всё в одной папке, без вложенных директорий)

```
index.html          — главная страница (сайт-визитка)
admin.html           — админ-панель
style.css            — единая стилизация (киберпанк / infosec тема)
script.js            — логика главной страницы
admin.js              — логика админ-панели
main.go               — backend на Go (REST API + отдача статики)
```

## Как это устроено

- Все данные (карточки проектов, профиль, заявки, пароль админа) хранятся в
  JSON-файлах (`data_projects.json`, `data_profile.json`, `data_leads.json`,
  `data_admin.json`), которые создаются автоматически при первом запуске
  рядом с сервером (или в `DATA_DIR`, если задана).
- Пароль администратора хранится в виде **соленого SHA-256 хэша**, не в
  открытом виде.
- Авторизация в админке — по токену (простая сессия в памяти сервера,
  живёт 24 часа).

## Запуск локально (без Docker)

Нужен установленный Go 1.22+.

```bash
go run main.go
```

Сайт будет доступен на `http://localhost:8080`,
админка — на `http://localhost:8080/admin.html`.

Пароль администратора по умолчанию: **changeme123**
(задайте свой через переменную окружения `ADMIN_PASSWORD` — см. ниже).
**Обязательно смените пароль** через вкладку «Безопасность» в админ-панели
сразу после первого входа.

## Запуск через Docker Compose (рекомендуется)

1. Скопируйте `.env.example` в `.env` и укажите свой пароль:
   ```bash
   cp .env.example .env
   # отредактируйте ADMIN_PASSWORD внутри .env
   ```
2. Запустите:
   ```bash
   docker compose up --build -d
   ```
3. Откройте `http://localhost:8080`.

Данные сохраняются в Docker-томе `site_data`, то есть переживают перезапуск
контейнера.

## Запуск через голый Docker (без compose)

```bash
docker build -t dzhdanov-site .
docker run -d -p 8080:8080 \
  -e ADMIN_PASSWORD=ваш_надежный_пароль \
  -e PORT=8080 \
  --name dzhdanov-site \
  dzhdanov-site
```

## Деплой на Railway

1. Создайте новый проект на Railway → **Deploy from GitHub repo**
   (залейте содержимое этой папки в репозиторий) **или** используйте
   Railway CLI / «Empty project → Docker image», указав, что сборка идёт
   по `Dockerfile` из корня репозитория.
2. Railway автоматически определит `Dockerfile` и соберёт образ.
3. В настройках проекта → **Variables** добавьте:
   - `ADMIN_PASSWORD` — ваш пароль администратора (обязательно смените
     значение по умолчанию!)
   - Railway сам подставит `PORT` — сервер уже читает эту переменную,
     ничего дополнительно делать не нужно.
4. Для сохранения данных между деплоями подключите **Railway Volume** и
   примонтируйте его в `/app/data`, дополнительно задав переменную
   `DATA_DIR=/app/data`. Без volume данные (карточки, заявки) будут
   сбрасываться к исходным при каждом новом деплое (но не при простом
   перезапуске контейнера).
5. После деплоя откройте выданный Railway домен — сайт готов.
   Админка — по адресу `/admin.html`.

## Админ-панель — что можно редактировать

- **Проекты (карточки)** — добавление / редактирование / удаление любой
  карточки, включая ссылку на демо/GitHub и стек технологий.
- **Профиль сайта** — имя, роль, email, Telegram, вводный текст на главной.
- **Заявки** — все обращения, отправленные через форму обратной связи на
  сайте.
- **Безопасность** — смена пароля администратора.

## API (если захотите расширить)

```
GET    /api/projects           — список всех карточек
GET    /api/projects/{id}      — одна карточка
POST   /api/projects           — создать (нужен токен)
PUT    /api/projects/{id}      — обновить (нужен токен)
DELETE /api/projects/{id}      — удалить (нужен токен)

GET    /api/profile            — данные профиля
PUT    /api/profile            — обновить профиль (нужен токен)

POST   /api/contact            — отправка формы обратной связи (публично)
GET    /api/leads              — список заявок (нужен токен)

POST   /api/login              — вход, возвращает { token }
GET    /api/admin/ping         — проверка токена
POST   /api/admin/password     — смена пароля (нужен токен)

GET    /healthz                — health-check для Railway
```

Авторизация: заголовок `Authorization: Bearer <token>`, токен выдаётся
эндпоинтом `/api/login`.

## Что уже сделано по безопасности

- Пароль хранится только в виде соленого хэша.
- Сравнение хэшей — через `constant time compare` (защита от timing-атак).
- Валидация входных данных на форме заявок (обязательные поля, ограничение
  длины).
- Заголовки `X-Frame-Options`, `X-Content-Type-Options`,
  `Referrer-Policy`.
- Экранирование данных при выводе на frontend (защита от XSS в карточках
  и заявках).
- `DisallowUnknownFields` в JSON-декодере API (защита от «мусорных» полей
  в запросах).

Для продакшена дополнительно рекомендуется: HTTPS (Railway выдаёт его
автоматически на своём домене), rate-limiting на `/api/login` и
`/api/contact`, ротация токенов/сессий через полноценное хранилище (Redis)
при росте нагрузки.

## Раздел «QR Guard PRO»

В hero-разделе сайта был текст про «международную сертификацию
безопасности» этого проекта — я убрал эту формулировку и заменил на
честное описание security-first подхода, потому что заявление о
сторонней сертификации, которое нельзя подтвердить ссылкой, — риск для
доверия, если заказчик спросит подробности. Если сертификация или аудит
реальны и есть на что сослаться — верните формулировку и добавьте ссылку
на подтверждение через раздел `#qrguard` в `index.html`.
